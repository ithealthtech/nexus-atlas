Security model

What Atlas protects, and from whom.

Atlas holds client documentation and credentials, so its protections — and their limits — are written down.

On this page

Every request

  1. Host and Originmust match PUBLIC_URL; cross-site requests are refused.
  2. The session cookie(HttpOnly, Secure, SameSite=Strict, __Host-) resolves to an active session, and every change carries its CSRF token.
  3. Sign-in stagesare complete: password, then two-step verification (required for staff), then any required password change.
  4. Client access— the highest of the person's baseline, grants, and groups, capped by their role — allows the action.
  5. Passwordsalso need edit-and-passwords access, pass restriction lists, and a reason when the client requires one. The reveal is recorded.

API keys replace the session steps with a hashed bearer key limited to its scopes and to the documentation and vault endpoints.

Threats and protections

Threat Protection
Stolen database or backup Passwords, notes, one-time code keys, MFA secrets, and the SMTP and Hudu credentials are encrypted with AES-256-GCM, bound to their row and field. Keys are wrapped by a master key that is never stored in the database. Backups are encrypted with a key derived from it.
Password guessing scrypt hashes, lockout after 5 failures, per-address rate limits, and MFA for staff. Passkeys can't be phished.
Stolen session Sessions expire after 2 hours idle or 12 hours; people can see and end their sessions; sensitive actions need the password again.
Cross-site attacks Host, Origin, and Sec-Fetch-Site checks, a per-session CSRF token, and a strict Content Security Policy with no inline or third-party scripts.
Over-broad access inside the MSP Per-client access levels, restricted passwords, required reasons, and an access history of every reveal, copy, change, and share.
Malicious uploads Stored outside the web root under random names. Only images that pass a content check display inline.
Tampering with the audit trail Security events are hash-chained by database triggers with a signed checkpoint. Verify now detects edited, reordered, and deleted events.
Leaked API key Stored as hashes, limited by scope, kept away from account, people, settings, backup, and log endpoints, and can expire.
One-time share links The password is encrypted in the browser; the key lives only in the link's #fragment, which the server never receives.

What it doesn't protect against

!

Administrators can read every password. Atlas is not end-to-end encrypted like a personal password manager. It records every read instead, and lets you restrict entries to named people.

  • Someone who has both the master key and the database.
  • A compromised server, administrator account, or signed-in person's device.
  • Server-side requests an administrator configures: the Hudu importer connects to any https:// address, including internal ones.
  • Rate limits across several servers: failed-attempt counters are per server, though account lockout applies everywhere.

Operating securely

  • Serve Atlas only over HTTPS, behind a reverse proxy with TRUST_PROXY=true.
  • Keep the master key in a password manager and on paper, not next to backups.
  • Keep backups off the Atlas server, and check them with npm run backup -w @atlas/server -- verify <file>.
  • Check System status and Security log → Verify now regularly.

Reporting a vulnerability

Never in a public issue. Use GitHub's private vulnerability reporting (Security → Report a vulnerability) with the affected version, impact, and steps to reproduce. See the security policy.
